# Test plan — REQ-160: Orders API contract

- **Requirement:** `requirements/REQ-160-orders-api.md`
- **Contract (frozen at sign-off):** `requirements/openapi/orders.yaml`
- **Target file:** `tests/generated/REQ-160.spec.ts` (one file — `inventory/tests.json` has a single row `T-0160-01` covering AC1–AC3)
- **Tag:** every test carries `{ tag: ['@REQ-160'] }`
- **Base URL:** `http://localhost:4173` (use `baseURL` from the config; do not hard-code it)

REQ-160 is an **API-level** requirement. Steps below are HTTP requests, not UI actions. The UI
journeys over the same behaviour already belong to REQ-142 and REQ-150 — do not re-test them here.

## Provenance of every assertion

Each assertion in this plan is tagged so a reviewer can see where it comes from:

- `[AC1]` / `[AC2]` / `[AC3]` — stated verbatim by an acceptance criterion.
- `[contract]` — stated by `openapi/orders.yaml`, which the requirement links and freezes at sign-off.

The generator may not drop either kind. If a `[contract]` assertion fails while its `[AC]` sibling
passes, that is still a real finding — escalate it, do not loosen it.

## Setup shared by every test

Use the **`request` fixture**, not `page`. Import `DEMO_USER` from `skills/fixtures` and
`CARDS`, `DEMO_CART_ITEMS`, `orderRequest` from `skills/data` — do not re-declare credentials,
card ids or cart items inline.

**Authenticating (playbook PB-002):**

```
POST /api/login   { email: DEMO_USER.email, password: DEMO_USER.password }
```

The response sets an HttpOnly `session` cookie, which the same `request` context keeps for
later calls. Assert the login itself succeeded (`200`) before the call under test, so a broken
login fails as a setup error rather than masquerading as an orders-API failure.

**Do _not_ use `page.clock.setFixedTime` or the `signedInPage` fixture in this file.**
Playbook PB-001 is about the *browser* clock. Card expiry for `/api/orders` is decided by the
**server**, which a Playwright API test cannot reposition. Determinism here comes from the test
data instead: `card_mc` expires `01/2025`, which is permanently in the past.

## AC1 — authenticated client POSTs a valid order

> WHEN an authenticated client POSTs a valid order to `/api/orders` THE SYSTEM SHALL respond `201`
> with a JSON body containing `id` (string), `total` (number), `currency` ("USD") and `status` ("confirmed").

### T1 — creates an order for a valid card

**Scenario name:** `creates an order and returns the confirmed order body`

**Preconditions**
- Authenticated as `DEMO_USER` on the `request` context (see setup).
- No clock manipulation.
- No assumption about pre-existing orders: this call **creates** one. Each run adds a new order to
  the demo AUT; nothing may depend on the store being empty or on a particular id.

**Steps**
1. `POST /api/login` with `DEMO_USER`; expect `200`.
2. `POST /api/orders` with `orderRequest(CARDS.valid.id)` —
   `{ cardId: 'card_visa', items: [{ sku: 'WID-1', qty: 2 }, { sku: 'GAD-7', qty: 1 }] }`.

**Expected outcome**
- Status is exactly `201`. `[AC1]`
- `content-type` response header contains `application/json` (match with `toContain`, not equality —
  a `; charset=utf-8` suffix is legitimate). `[contract]`
- The body parses as JSON and has all four required properties `[AC1]` `[contract: Order.required]`:
  - `typeof body.id === 'string'`, and `body.id` is not the empty string (an id that identifies
    nothing does not satisfy the contract). `[AC1]`
  - `typeof body.total === 'number'`. `[AC1]`
  - `body.currency === 'USD'` exactly. `[AC1]`
  - `body.status === 'confirmed'` exactly. `[AC1]`

**Explicitly do not assert**
- **A value for `total`.** AC1 promises only *a number*. The `35.5` in the contract is an `example`,
  and the figure is REQ-150's promise, already covered by `tests/checkout/order-total.spec.ts`.
  Asserting it here would test a requirement this file does not own.
- **A format for `id`.** The contract says `string`. Exploration showed `ord_bef6af25` on the
  confirmation page, but `ord_<hex>` is an implementation detail — a regex over it would over-fit.

### T2 — negative case implied by "a *valid* order" (contract-derived)

**Scenario name:** `rejects an order with no card id`

**Preconditions:** authenticated exactly as T1.

**Steps**
1. `POST /api/login` with `DEMO_USER`; expect `200`.
2. `POST /api/orders` with `{ items: DEMO_CART_ITEMS }` — `cardId` omitted, which violates
   `OrderRequest.required: [cardId, items]`.

**Expected outcome**
- Status is exactly `400`. `[contract: 400 "Invalid request body"]`
- Body parses as JSON and `typeof body.error === 'string'` and is non-empty.
  `[contract: Error.required: [error]]`

**Do not assert a particular `error` string.** The contract's `card_expired` is an `example` on the
shared `Error` schema, not the value for `400`. No AC pins a message for an invalid body.

## AC2 — unauthenticated client POSTs

> WHEN an unauthenticated client POSTs to `/api/orders` THE SYSTEM SHALL respond `401`.

### T3 — rejects an unauthenticated POST

**Scenario name:** `rejects an order from a client that is not signed in`

**Preconditions**
- **No login at all in this test.** The request context must carry no `session` cookie.
- This is safe by construction: Playwright's `request` fixture is per-test, and
  `playwright.config.ts` sets no `storageState`. The generator must **not** share a context with
  T1/T2/T5, and must not call `/api/login` here — a leaked cookie would turn this test green for
  the wrong reason.

**Steps**
1. `POST /api/orders` with `orderRequest(CARDS.valid.id)` — an otherwise **valid** body, so the only
   thing wrong with the request is the missing session.

**Expected outcome**
- Status is exactly `401`. Assert the number — not `res.ok()`, not `expect(res.status()).not.toBe(201)`.
  A `403`, `400` or `500` here is a failure, and a loose assertion would hide it. `[AC2]`
- Body parses as JSON and `typeof body.error === 'string'` and is non-empty.
  `[contract: 401 response, Error.required: [error]]`

### T4 — negative case implied by "unauthenticated"

**Scenario name:** `rejects an order sent with a forged session cookie`

**Preconditions:** no login. A client holding an unrecognised `session` value is, by definition,
unauthenticated — so AC2 governs it.

**Steps**
1. `POST /api/orders` with `orderRequest(CARDS.valid.id)` and header
   `Cookie: session=not-a-real-session`.

**Expected outcome**
- Status is exactly `401`. `[AC2]`

If the AUT returns `201` here it is accepting any cookie value as a session — a real auth defect, not
a test problem. Escalate (`type: aut_bug`) rather than relaxing this test.

## AC3 — order uses an expired card

> WHEN the order uses an expired card THE SYSTEM SHALL respond `422` with `{"error":"card_expired"}`.

### T5 — rejects an expired card

**Scenario name:** `rejects an order paid with an expired card`

**Preconditions**
- Authenticated as `DEMO_USER` (an expired card must be rejected on its own merits, with
  authentication out of the way — otherwise a `401` would satisfy "not 201" and hide the defect).
- `CARDS.expired.id` is `card_mc`. Confirmed on the running app: the checkout radio reads
  **"Mastercard •••• 4444 (expires 01/2025)"**. That date is permanently in the past, so this test
  is stable without touching any clock.

**Steps**
1. `POST /api/login` with `DEMO_USER`; expect `200`.
2. `POST /api/orders` with `orderRequest(CARDS.expired.id)` —
   `{ cardId: 'card_mc', items: [{ sku: 'WID-1', qty: 2 }, { sku: 'GAD-7', qty: 1 }] }`.

**Expected outcome**
- Status is exactly `422`. `[AC3]`
- The parsed body **equals** `{ error: 'card_expired' }` — deep equality (`toEqual`), not merely
  `body.error === 'card_expired'`. AC3 writes out the whole object, so an extra or missing key is a
  contract break. `[AC3]`

**No extra negative test.** The complement of AC3 — a non-expired card must *not* be rejected — is
precisely T1. Adding another would duplicate it.

## Deliberately out of scope

Named so a reviewer can see these were considered, not missed:

- **Unknown card id.** The contract's `422` covers "Card unknown **or** expired", but no acceptance
  criterion states a status or body for an unknown card. Testing it would be inventing behaviour.
- **Order persistence / retrieval.** Neither the contract nor `memory/app-model.json` exposes a
  `GET /api/orders`, so "no order was created on a 401/422" is not observable. Not asserted.
- **The value of `total`, and the `$35.50` UI figure.** REQ-150, already covered.
- **UI payment flows.** REQ-142, already covered.
- **`/api/login` behaviour itself** (including its `401`). REQ-101 and the contract's login path; here
  login is setup only.

## Risks for the human reviewer

1. **`card_visa` expires 12/2030.** T1 and T4 use it as the valid card. Because the server clock
   cannot be fixed from an API test, both will start returning `422` after 2030-12-31 — a false
   failure with no in-test workaround. The fix is new fixture data, which is a human change to
   `skills/data.ts`. Flagging now; no action needed in this run.
2. **T1 has a side effect.** Every run creates a real order in the demo AUT. With
   `--repeat-each=5` that is five orders. Nothing in this plan depends on order count, so this is
   safe, but a future test that lists orders must not assume a clean store.

## What exploration did and did not verify

Signed in at `http://localhost:4173` as `demo@example.com` and walked the checkout journey:
cart (Widget ×2 @ $10.00, Gadget ×1 @ $15.50, Total $35.50), paid with Visa → `/confirmation?id=ord_bef6af25`
with heading "Order confirmed"; paid with Mastercard •••• 4444 → stayed on `/checkout` with the alert
"This card has expired. Update card to continue."

The UI behaviour is consistent with AC1 and AC3. **The API responses themselves were not verified** —
raw HTTP calls are outside the planner role's permitted tools, so no status code or response body
below was observed first-hand. No `aut_bug` escalation is filed: nothing observed contradicts the
requirement, and guessing at one would be noise. The generator runs these tests for real and will
surface any violation.
