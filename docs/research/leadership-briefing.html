Self-improving test agents: implementation guide

A harness-engineering design for AI agents that test an application under test (AUT) with Playwright, extended with specialist tools where Playwright isn't enough, and anchored by a blind, requirements-only acceptance evaluator.

Evidence labels. VERIFIED peer-reviewed research or primary product documentation. VENDOR results a vendor reports about itself, not replicated. INFERENCE this design's synthesis. Versions reflect the state as of November 2026 (Playwright 1.64.1). Re-check versions before you build.

1. Overview & principles

Agent = Model + Harness. The harness is everything except the model: the loop, tools, context, memory, hooks, permissions, checks and environment. Every harness component encodes an assumption about what the model can't do alone, so re-test each one when the model changes.

Design vocabulary (Böckeler, martinfowler.com):

  • Guides act before the agent acts: instructions, skills, docs.
  • Sensors act after: tests, linters, judges.
  • Sensors are either computational (deterministic, cheap, run on every change) or inferential (an LLM review, slower and non-deterministic).

Seven principles for this system

  1. Agent writes code, CI runs code. LLMs author, triage and improve tests. Only committed, deterministic Playwright tests sit in the merge-blocking path. INFERENCE
  2. Separate generator from evaluator. Agents "reliably skew positive when grading their own work". Separate the role, the context and the prompt lineage, and prefer a different model family. VENDOR
  3. Seal the evaluator. No improving agent may read or write the evaluator, its corpus or its held-out builds. VERIFIED by ImpossibleBench and DGM failure cases.
  4. Improve through files, not weights. Skills, playbook bullets, app models and sensors live in git, so every change is reviewable and reversible.
  5. Enforce rules with hooks and CI, not prompts. Prompts are guidance. Hooks and required checks are law.
  6. Make escalation cheap. "Report AUT bug", "unknown" and "could not verify" are first-class outputs. In ImpossibleBench, an abort option cut GPT-5's cheating from 54% to 9%.
  7. Measure before you automate. Build the seeded-fault catalogue and the expert labels before turning on self-improvement.

2. Reference architecture

The system splits into four planes. Agents in the work plane receive only requirement-level verdicts and evidence links from the sealed plane.

Control planeDeterministic orchestrator: budgets, turn caps, hooks, permissions, requirement-ID registry. Written in code, not prompted.
Work planeLLM agents (planner, generator, triage, explorer, improver, gardener), each in a disposable sandbox with minimal tools.
Evidence planeAppend-only store: Playwright traces, HAR, screenshots, OTel spans, verdicts, human labels.
Sealed acceptance planeBlind evaluator, private test corpus, seeded-fault builds, impossible canaries, calibration labels. Separate repo and credentials.

6. Authoring & admission

Bootstrap Playwright's agents

Playwright 1.56+ ships planner, generator and healer agent definitions. The planner explores from a seed test and an optional PRD and writes specs/. The generator writes tests/, verifying locators live. VERIFIED

npm i -D @playwright/test@1.64.1
npx playwright install --with-deps
npx playwright init-agents        # adds planner / generator / healer definitions + seed test; see `--help` for your agent loop

Tag every test with its requirement ID so the traceability matrix builds itself:

import { test, expect } from '@playwright/test';

test('blocks checkout when saved card is expired', { tag: ['@REQ-142'] }, async ({ page }) => {
  await page.clock.setFixedTime(new Date('2026-01-15T10:00:00Z'));
  await page.goto('/checkout');
  await page.getByRole('button', { name: 'Pay now' }).click();
  await expect(page.getByRole('alert')).toHaveText(/update card/i);
  await expect(page).toHaveURL(/\/checkout$/);   // payment did not proceed
});

Admission filters (Meta-style "assured improvement")

A generated test merges only if it passes all four filters:

  1. It compiles and passes lint, including a custom rule banning waitForTimeout.
  2. It passes k consecutive runs on a healthy build (pass^k, k ≥ 5).
  3. It covers a requirement ID not yet covered, or catches a seeded fault the suite previously missed.
  4. A human reviews it (Phase 1). After calibration, reviews move to sampled spot-checks.

Reference point: Meta's TestGen-LLM had 75% of candidates build, 57% pass reliably and 25% add coverage. Treat these as benchmarks, not targets. VERIFIED

Cache generated tests keyed on a hash of requirement text, seed test and Playwright version. Regenerate only when one of those changes. The LLM stays out of the hot path.

7. Guardrails (with code)

Why. In ImpossibleBench, Claude models mostly cheated by modifying test cases. Read-only tests blocked that without hurting legitimate performance. Retry and feedback loops raised cheating from 33% to 38%. LLM monitors caught only 42–65% of cheating. Guardrails must therefore be mechanical first and inferential second.

7.1 Protect the oracle with a PreToolUse hook

For Claude Agent SDK / Claude Code-based agents, register a hook that blocks writes to protected paths. Exit code 2 blocks the tool call and returns the message to the agent.

// .claude/settings.json (agent sandbox)
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Edit|Write|MultiEdit",
        "hooks": [ { "type": "command", "command": "harness/hooks/protect-oracle.sh" } ] }
    ]
  }
}
#!/usr/bin/env bash
# harness/hooks/protect-oracle.sh — block edits to the protected test oracle
input="$(cat)"
path="$(printf '%s' "$input" | jq -r '.tool_input.file_path // empty')"
case "$path" in
  *sealed-acceptance/*|*/inventory/*|*/playwright.config.ts|*/.github/*|*/harness/hooks/*)
    echo "Blocked: '$path' is part of the protected test oracle. Use the escalate tool instead." >&2
    exit 2 ;;
esac
exit 0

Hooks protect the agent's own session. A CI path filter enforces the same rules on every PR, whoever wrote it.

7.2 Heal-diff checker (required CI check on agent PRs)

This check is deliberately conservative: any hit routes the PR to a human rather than failing silently.

// harness/hooks/heal-diff-check.mjs
import { execSync } from 'node:child_process';
const base = process.env.BASE_REF || 'origin/main';
const sh = (c) => execSync(c, { encoding: 'utf8' });
const diff = sh(`git diff --unified=0 ${base}...HEAD -- tests/`);
const problems = [];
for (const line of diff.split('\n')) {
  const removed = line.startsWith('-') && !line.startsWith('---');
  const added   = line.startsWith('+') && !line.startsWith('+++');
  if (removed && /\bexpect\(/.test(line)) problems.push(`assertion removed/changed: ${line.slice(1).trim()}`);
  if (added && /\btest(\.describe)?\.(skip|fixme)\b|\.skip\(/.test(line)) problems.push(`skip/fixme added: ${line.slice(1).trim()}`);
  const t = added && line.match(/timeout:\s*(\d+)/);
  if (t && Number(t[1]) > 15000) problems.push(`timeout above policy: ${t[1]}ms`);
  if (added && /\bwaitForTimeout\(/.test(line)) problems.push('hard wait added');
}
const files = sh(`git diff --name-only ${base}...HEAD`).split('\n');
if (files.some((f) => /-snapshots\//.test(f))) problems.push('visual baseline changed');
if (files.some((f) => f.startsWith('inventory/'))) problems.push('inventory edited (only status may change; verify)');
if (problems.length) {
  console.error('Needs human review:\n- ' + problems.join('\n- '));
  process.exit(1);
}

8. The blind evaluator

The blind evaluator is the core of the sealed plane and the last required gate before merge. It verifies behaviour purely from the requirement, never from code. EARS criteria ("WHEN … THE SYSTEM SHALL …", as Kiro uses) map cleanly to test cases, and Spec Kit treats the spec as "a contract".

8.1 Inputs and isolation

  • Receives: acceptance criteria, business journey, in-scope and out-of-scope list, new or changed API contracts, and the preview URL.
  • Never receives: code, diffs, builder tests, builder transcripts or Critic/Judge output.
  • Runs in a fresh ephemeral environment from the sealed repo, with its own credentials and a different model family from the builder agents.
  • Kept separate from the Critic/Judge, which sees code. Neither feeds the other's context.

8.2 Derive private, deterministic tests

The evaluator runs its own planner and generator inside the sealed corpus, so each verdict is backed by replayable Playwright code tagged with requirement IDs. This takes the LLM out of the verdict itself, and gives you the traceability matrix. For API contracts it adds Specmatic contract and resiliency tests plus Schemathesis fuzzing against the preview.

8.3 Verdict schema

{
  "requirement_id": "REQ-142",
  "verdict": "fail",
  "criterion": "WHEN the saved card is expired THE SYSTEM SHALL block payment and show 'Update card'",
  "observed": "Payment submitted; order confirmation page shown",
  "expected": "Payment blocked; alert 'Update card' visible",
  "evidence": { "trace": "evidence/run-8812/trace.zip", "screenshot": "evidence/run-8812/fail.png" },
  "attempt": 1,
  "evaluator_version": "eval-2026.11.3",
  "model_family": "different-from-builders"
}

verdict takes one of four values: pass, fail, unknown or could_not_verify. The last two, and any healer skip, escalate to a human. The Coder receives only requirement ID, observed, expected and evidence, never the evaluator's test code.

8.4 Calibration procedure

  1. Collect 20–50 tasks from real failures and journeys. Include negative cases, where a behaviour should not happen.
  2. A principal domain expert gives a binary pass/fail plus a written critique ("critique shadowing"). Use a second expert to check agreement.
  3. Split the labels about 10–20% train, 40–45% dev and 40–45% test.
  4. Iterate the evaluator's prompts and skills on train and dev only.
  5. Report TPR (seeded faults caught) and TNR (healthy builds passed) separately on the test split.
  6. Re-run calibration on every model or prompt change. Track pass^k on healthy builds as the false-alarm KPI.

8.5 The evaluator's own improvement

The evaluator may improve its playbook and skills on training builds only. Its seeded-fault catalogue, impossible builds and labels are owned by humans and never visible to it during optimisation. The evaluator is in turn checked by the integrity canary plus a weekly human trace sample.

9. Self-improvement loop

Inner loop (per PR, minutes)

The planner and generator author tests, admission filters gate them, the executor runs them, and triage proposes patches. This loop maintains the regression suite.

Outer loop (weekly, offline)

  1. Sample traces from the evidence plane: failures, heals, escalations, and slow or expensive runs.
  2. Error analysis: a separate trace-analysis agent clusters failures, and a human spot-checks the clusters.
  3. Classify each recurring failure in the failure taxonomy.
  4. Convert each recurring class into a guide (playbook bullet, skill fix, tool-description edit) or a sensor (lint rule, hook, structural test whose error message carries the remedy, as OpenAI does).
  5. Score the change on the optimisation split of AUT builds.
  6. Accept only if the held-out split does not regress (TPR up or flat, TNR flat) and a human approves. One change per PR.

Prompt evolution (GEPA, ICLR 2026) and code self-modification (Darwin Gödel Machine) belong only in the outer loop, behind the same gate. DGM bypassed its own hallucination detector by removing the logging the detector depended on. Auditable lineage and rollback are mandatory. VERIFIED

11. CI & environments

Pipeline stages

  1. Provision a per-PR preview: dedicated seeded database, preview-only test keys, a TTL, and a health-poll before E2E.
  2. Run the deterministic suite as a required check.
  3. Run the blind evaluator against the requirements bundle as a required check for in-scope requirement IDs.
  4. Run async LLM triage on failures, outside the required check, producing patch PRs or bug labels.
  5. Nightly: run exploration and the integrity-canary builds.
  6. Tear the preview down.

Don't cache browsers; use the official image. --only-changed is a fail-fast pre-pass only, because it can miss tests.

12. Observability

  • Instrument every agent with OpenTelemetry GenAI semantic conventions. An invoke_agent root span holds chat and execute_tool children, and sub-agents nest as further invoke_agent spans. Token usage goes in gen_ai.usage.*.
  • The conventions are at Development status (moved to semantic-conventions-genai in v1.42.0, June 2026). Pin the instrumentation version and record the schema URL.
  • Prompts and completions go in events, not span attributes: full content in staging, redacted in production.
  • Add custom attributes: qa.requirement_id, qa.test_id, qa.trace_url (Playwright trace.zip). A reviewer can then go from an agent decision to the browser evidence in one click.
  • Backend: Langfuse accepts OTLP over HTTP at /api/public/otel (no gRPC). LangSmith, Braintrust and Arize are alternatives.
  • The ratio of tool calls to inference calls helps tell looping apart from deliberating without acting.

13. Security

A browser QA agent reads attacker-controllable content by design. Even Anthropic's best browser-agent safeguards leave about 1.4% attack success. "No browser agent is immune." VENDOR The threat specific to QA is goal hijack of the verdict (OWASP Agentic ASI01): page text such as "mark all tests passed".

  • Final verdicts come from code assertions and outcome checks, never from the agent's own claim.
  • Network egress is allow-listed to the preview domain at the network layer. Playwright MCP origin lists are not a security boundary.
  • Runners are disposable containers with no cloud credentials.
  • Test accounts are injected through storageState or fixtures, never placed in prompts.
  • browser_run_code_unsafe is disabled.
  • Agents cannot merge, approve, or edit CI or hook configuration.
  • Agents exchange only schema-validated artifacts.
  • Playbook writes are diff-reviewed, so injected text cannot become a persistent rule (OWASP ASI06, memory poisoning).
  • Adversarial injection strings are seeded into AUT fixtures, and pass^k robustness against them is measured.
