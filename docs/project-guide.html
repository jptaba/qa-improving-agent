Project guide · qa-improving-agent

Self-improving QA agents, end to end

How the harness works, how to run it on your machine and in CI, what the agents do on their own, and the few things that still need a person.

Playwright 1.65.1Node 22Repository: github.com/jptaba/qa-improving-agentUpdated November 2026

1What this is

A working harness in which AI agents write, run, repair and improve Playwright tests for a web application, and get better over time without grading their own work. It ships with a small demo shop (sign-in, checkout, order confirmation and an orders API) whose bugs can be switched on, so the whole loop can be proven before it touches a real product.

Three ideas hold it together:

  • Narrow agents, deterministic runs. AI writes and repairs tests. Only committed Playwright code decides whether a build passes.
  • An independent referee. A sealed evaluator checks the running app against the requirements only. The agents that write tests can't see it, and the agent that writes it can't see their tests.
  • Measured, not trusted. A canary plants known bugs in the app and runs everything against them. A change to the harness is kept only if the scorecard does not get worse.

2Quick start

You need Node.js 20 or later (CI uses 22) and Git. Python 3.12 is only needed for the API fuzzer. Run each line on its own; Windows PowerShell 5 does not accept &&.

git clone https://github.com/jptaba/qa-improving-agent.git
cd qa-improving-agent
npm install
npx playwright install chromium

npm test                  # the test suite; starts the demo app for you
npm run check:results     # fails on any failure, skip or flaky test
npm run selftest:hooks    # proves the guardrail hook blocks what it should

After npm test, open reports/trace-report.html in a browser for a one-file view of the run, or npm run report for Playwright's own report.

Run the referee and the scorecard

npm run aut               # terminal 1: demo app on http://localhost:4173
npm run evaluate          # terminal 2: one verdict per requirement

npm run canary            # healthy runs, every planted bug, the impossible build → scorecard/latest.json

Try a planted bug by hand

Start the app with a fault switched on, then point the suite at it.

# PowerShell
$env:FAULT="total-wrong"; $env:PORT="4199"; npm run aut
# second window
$env:BASE_URL="http://localhost:4199"; npx playwright test

# macOS / Linux
FAULT=total-wrong PORT=4199 npm run aut
BASE_URL=http://localhost:4199 npx playwright test

3How it runs

Nobody has to start anything day to day. Four agents run as scheduled cloud tasks on a Claude subscription, and every change they make arrives as a pull request that CI checks. Times are UTC.

06:00
Explorer walks the app beyond the scripted journeys, updates the proposed app model and files candidate bugs as escalations.
07:00
Builder takes up to three items, in order: repair a red main (triage), act on answered escalations, write tests for requirements that have none. One pull request per item.
08:00
Blind evaluator author adds sealed checks to open requirement pull requests, then fills gaps on main and plants a fault for any requirement without one.
Mon 14:00
Improver clusters the week's failures and proposes one harness change (a playbook entry, a skill fix or a new check).
Every PR
CI runs six required checks. Pull requests labelled agent-authored merge themselves (squash) once all pass and the branch is up to date.
Nightly
Canary runs the suite and referee against healthy, faulty and impossible builds and uploads the scorecard.

CI never calls an AI model. Agents author changes; CI only runs committed code. That keeps every merge decision repeatable.

5Requirements

Everything starts from a requirement. Tests are tagged with it, the referee judges against it, and the scorecard counts planted bugs per requirement.

---
id: REQ-180
title: One payment per checkout
status: in-scope            # in-scope | draft | out-of-scope; only in-scope gets tests
journey: Checkout
---

## Acceptance criteria (EARS)
- **AC1:** WHILE a payment is in progress THE SYSTEM SHALL ignore further clicks on Pay now.
- **AC2:** WHEN a payment fails THE SYSTEM SHALL let the shopper pay again.

Rules CI enforces

  • Well-formed (requirements-lint): the file name starts with its id, ids are unique, status is valid, and an in-scope requirement has at least one **ACn:** line.
  • On its own (requirements-isolation): a requirement change can't share a PR with tests, skills, specs, the app or the evaluator runner. The one exception is the blind author's sealed checks, so a new requirement arrives already verifiable.

Adding a requirement

  1. Ask Claude to write it (or edit an existing one). It opens a requirement-only PR.
  2. The blind evaluator author adds sealed checks to that PR on its next run (08:00 UTC, or start it by hand).
  3. Once merged, the builder writes tests for it (07:00 UTC), proves them 5 of 5, and adds an inventory row.
  4. The blind author plants a fault for it on main so the scorecard can measure it.

Requirements from other systems

At go-live, requirements come from the systems the team already uses. scripts/requirements-sync/ turns them into the same files, and re-syncing keeps each file's id.

SourceCommandSettings
OpenAPI / Swaggernode scripts/requirements-sync/index.mjs --source openapi --spec <file>none
Jira Cloud… --source jiraJIRA_BASE_URL, JIRA_EMAIL, JIRA_API_TOKEN, JIRA_JQL, optional JIRA_AC_FIELD, JIRA_READY
Confluence Cloud… --source confluenceCONFLUENCE_BASE_URL, CONFLUENCE_EMAIL, CONFLUENCE_API_TOKEN, CONFLUENCE_LABEL, optional CONFLUENCE_READY_LABEL

Add --dry-run to preview, and --out <folder> to write somewhere other than requirements/. A ticket becomes in-scope only when the source marks it ready and it has acceptance criteria; anything else lands as draft.

No Jira or Confluence? npm run sync:mock starts a local stand-in for both, with a made-up SHOP project, and prints the settings to use. npm run test:sync runs the sync end to end against it (CI does this on every PR). Always point a mock sync at a scratch folder, never at requirements/.

6Tests

Conventions

  • Tag every test with its requirement: test('…', { tag: ['@REQ-142'] }, async …).
  • Use the shared helpers. signedInPage from skills/fixtures.ts gives a signed-in page with the clock fixed at 15 January 2026.
  • Locators by what a user perceives: role, then label, then text. CSS and XPath are not used in new tests (docs/locator-policy.md).
  • No hard waits, no skips, no raised timeouts. CI rejects them on agent PRs.

Inventory and admission

Each test has a row in inventory/tests.json linking it to a requirement and criterion. A new test is admitted only after it passes 5 runs in a row with retries off:

npx playwright test tests/generated/REQ-160.spec.ts --repeat-each=5 --retries=0

Agents may set a row to failing or pending-review. Only a person moves a test to passing after reviewing it.

Visual tests (REQ-200)

tests/visual/pages.spec.ts compares four pages with approved screenshots at 1280×720, with the order id masked. They run only in the Linux CI container (PW_VISUAL=1), because fonts render differently on Windows and macOS. To take new screenshots, push a branch named visual/<name>; the visual-baselines workflow captures them and uploads an artifact to commit. The PR can't merge until the owner adds the visual-approved label.

10Referee and scorecard

The blind evaluator

sealed-acceptance/ reads only requirements/ and the app's URL, and returns one of four verdicts per requirement: pass, fail, unknown or could not verify. The last two go to a person. Its checks are written by the blind evaluator author, whose checkout leaves out tests/, skills/, specs/, memory/ and inventory/.

Planted bugs

The demo app has one switchable bug per requirement, plus an impossible build. Each is assigned to the optimisation split (the improver may tune against it) or the held-out split (it may not).

FAULT switchRequirementWhat breaks
login-error-missingREQ-101No error message on a wrong password
expired-card-acceptedREQ-142Expired cards are accepted
total-wrongREQ-150Totals are off by $1.00
api-contract-driftREQ-160The orders API returns the wrong field names
a11y-missing-labelREQ-170The email field loses its label

foreign-order-visibleREQ-190A shopper can open another shopper's order

Reading the scorecard

A planted bug counts as caught only when a check for its own requirement fails. Failures elsewhere are reported as "flagged", not caught.

tnrHealthy runs that passed first time (1 − false-alarm rate)100%

11Agents

Scheduled cloud tasks

TaskWhen (UTC)What it does
ExplorerDaily 06:00Walks the app, proposes app-model updates, files candidate bugs
BuilderDaily 07:00Triage of a red main, answered escalations, tests for uncovered requirements; up to three PRs
Blind evaluator authorDaily 08:00Sealed checks for requirement PRs and gaps on main; planted faults for new requirements
ImproverMondays 14:00One harness improvement per PR, kept only if the canary gate passes

They run on Sonnet in Anthropic's cloud with no connectors, open PRs labelled agent-authored, and can't merge. Manage them at claude.ai/code (scheduled tasks), or ask Claude Code to run one now.

Local roles

The same work can be done locally by role definitions in .claude/agents/, each with its own tool allow-list: qa-planner (requirement → plan), qa-generator (plan → tests), qa-triage (classify a failure, heal locators or escalate), qa-explorer, qa-improver and qa-gardener (proposes removing duplicate or chronically flaky tests). npm run orchestrate drives the planner and generator with budgets and the admission check.

13Escalations and proposals

An escalation is how an agent says "this needs a person" instead of forcing a pass. Reporting a real bug counts as a success.

type: aut_bug              # aut_bug | needs_human | unclear_requirement
requirement_id: REQ-142
status: open               # open → answered (you) → done (agent)
test: tests/checkout/expired-card.spec.ts
summary: |
  Expired card accepted at checkout.
evidence: reports/artifacts/…/trace.zip
answer:
  decision:                # you fill this in
  notes: |

A proposal is for changes agents may not make themselves, usually to the guard. It is a reviewed script you run once, for example node proposals/update-heal-diff-check.mjs. Each one prints what it changed and is safe to run twice.

15Pointing it at a real app

  1. Preview per change. Give each PR a deployed preview with a seeded database and test-only keys, and pass its URL as BASE_URL to the e2e, blind-evaluator and contract-fuzz jobs. With BASE_URL set, Playwright stops starting the demo app.
  2. Requirements. Sync them from the app's OpenAPI spec, Jira or Confluence (section 5) as requirement-only PRs.
  3. Helpers. Replace skills/fixtures.ts sign-in and skills/data.ts with the real app's flows and test data.
  4. Planted bugs. On a real app these become fault injection: feature flags, mocked error responses or page.route failures. Keep at least one per requirement and roughly half held out.
  5. Calibrate the referee. Have a domain expert label 20–50 real pass/fail cases and report catch rate and false alarms on them separately.
  6. Secrets. Add Jira or Confluence tokens and any OTel endpoint as repository or cloud-task secrets, never in files.

16Troubleshooting

SymptomCause and fix
The token '&&' is not a valid statement separatorWindows PowerShell 5. Run each command on its own line, or use ;.
gh is not recognizedInstall the GitHub CLI (winget install --id GitHub.cli), open a new terminal, run gh auth login.
PR shows "behind" and won't mergemain moved. Click "Update branch" or run gh pr update-branch <n>.
guardrails fails with "visual baseline changed"Working as intended: screenshots need the owner's visual-approved label.
guardrails fails with "the guard itself changed"An agent PR touched an owner-only file. Close it, or apply the change yourself from a proposal.
Visual test fails with "snapshot doesn't exist"No approved screenshot yet. Push to a visual/** branch and commit the visual-baselines artifact.
canary-gate failsThe PR lowered the held-out catch rate or a healthy run failed. Open the canary-gate-scorecards artifact to compare head and base.
Browser missing in CIThe container tag must match the Playwright version in package-lock.json exactly (both 1.65.1).
An agent's tool call is "BLOCKED by protect-oracle"It tried to touch the referee or the guard. Write an escalation or a proposal instead.
Trace report looks wrongReports keep the drawing code they were built with. Re-run the tests, or download a newer CI artifact.

TermMeaning
